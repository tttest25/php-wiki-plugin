# PHP-05 — Карточка завершённого задания

Из строки completed/failed пользователь откроет карточку с job ID, process ID, инструментом, статусом, датами и публичным результатом либо локализованным сообщением. Открытие и закрытие сохраняют текущую страницу журнала и фильтр; даже у двух заданий одного процесса результат относится только к выбранному job.

## Почему сейчас и что подтверждено

- Первый открытый шаг `/opt/php-wiki-plugin/docs/todo.md`, тот же порядок в `docs/php_wiki_jobs_roadmap.md`. PHP-04 закрыт в todo и реализован: `PetarClient::listJobs`, `syntax.php::renderJobs`, `script.js::initializeJobs/makeRow`, тесты `TestJobsAction`, `TestJobsUIBehavior`. Чекбоксы исторической карты отстают. Сейчас строка содержит шесть текстовых ячеек; `action.php::handleAjax` пропускает только readyz/submit/jobs. Маршрута чтения результата нет.
- В `/opt/go-pet` T26 закрыт в `todo.md`, коммит `eb27bfe`. `internal/api/server.go` регистрирует `GET /api/v1/jobs/{id}/result`; `internal/api/job_result.go::handleGetJobResult` берёт статус по job UUID и только для completed читает соответствующий `public.json`. 200 — сам JSON-объект (ровно `type`: непустая строка, `version`: 1, `data`: объект); максимум 1 048 576 байт **включительно**. 202 — `{status}` для pending/dispatched/in_progress; 409 — `error: job_failed`; 404 — неизвестный job; 410 — `error: result_unavailable`; 500 при превышении (`result_too_large`) без частичного документа. Некорректный ID — 400. Есть и инфраструктурные ошибки. Не считать любой не-200 «job failed».
- Доказательства в исходниках backend: `TestGetJobResultSelectsRequestedJob`, `TestGetJobResultStates`, `TestGetJobResultFileErrors`, `TestGetJobResultSizeLimit`. Это проверка кода и тестов, не новый прогон и не свидетельство развёртывания. В плагине `tests/acceptance/fixture.js` пока выдаёт одну строку и не обслуживает result. Ниже RED — прогноз, его должен зафиксировать Build.

2. **Граница BFF:** расширить тот же тест вариациями, при необходимости `tests/contract/client_test.go`. После happy path ошибки ещё не различаются. Не использовать `getStatus()`.
3. **Ответы T26:** тест → минимальная нормализация в клиенте → безопасный ответ. Для 200 валидировать конверт и размер исходного тела (проверки границы и превышения); сохранить `{}` объектом, не превращать в `[]`. Для 202 пропустить только три штатных статуса; 409 распознать только по `job_failed`, 410 по `result_unavailable`, 404 сообщать как отсутствие. BFF сохраняет эти HTTP-статусы и выдаёт только собственные фиксированные коды состояния/ошибки плюс request ID, без сырого диагностического текста; ошибочный конверт, неожиданный upstream код, сбой транспорта, 3xx, backend 500/таймаут → безопасный 502 без частичного результата. Проверить 409 с подменённой диагностикой, 200 с лишним полем, неверной версией и не-объектом `data`, редирект без перехода. Успешный `result` — только публичный документ, метаданные job берутся из строки, а не из произвольных полей backend.
4. **Журнал:** расширить `TestJobsUIBehavior` (`tests/contract/ui_test.go`, `ui_behavior.js`) и проверку разметки. Изначально кнопок и карточки нет. Добавить в `syntax.php::renderJobs` и `script.js::initializeJobs` доступное управление кнопками только для completed/failed и область карточки внутри конкретного виджета; RU/EN в `lang/{ru,en}/lang.php`. Рендер значений как текста; 200 показывает публичный JSON текстом, 409 — штатное локализованное сообщение, 202/404/410 и техническая ошибка различимы. Никакого автоматического polling/retry. Закрытие не перезагружает таблицу и не сбрасывает курсор. Два job с одинаковым process_id, разные маркеры: клик A, затем B, запоздалый ответ A не заменяет B; при новом выборе сразу убрать старый результат. Закрытие, обновление или смена фильтра инвалидируют незавершённое чтение; независимые виджеты. Проверить, что `response.ok` для 202 не трактуется как результат. Не вводить реестр представлений PHP-07, каталог, скачивание или новый макрос.
