## Контракт и наблюдаемая исходная точка

- `action.php::handleAjax()` допускает readyz/submit/jobs/job_result; затем читает POST tool/message/pattern. `PetarClient::submitInput()` проверяет статический список и вызывает `/api/v1/inputs`. В `syntax.php::render()` тот же статический список, `script.js::initialize()` разрешает submit после одной readiness. `tests/contract/action_test.go::actionPHP`, `client_test.go`, `TestUIRenderer`, `TestUIBehavior` и acceptance fixture/smoke привязаны к прежнему вводу.
- Согласовано: **замена**, не поддержка двух контрактов. AJAX `action=actions` (GET) → `{actions:[{action,version,title},…],request_id}`; `action=submit` (POST) остаётся диспетчером, не именем выбранной операции. Поля POST: `sectok`, `action_name`, `version` (десятичная положительная версия), `data` (текст одного JSON-значения). Диспетчер указывать в query; не помещать выбранное действие в одноимённый параметр `action`. Backend получает ровно `{action,version,data}`, JSON-версия — число. Старый формат с валидным CSRF → 400 без сети. Каталог недоступен или пуст → submit закрыт, старого списка нет.
- Новые методы `PetarClient::listActions` и `submitAction`; удалить `submitInput` и whitelist допустимых действий. Фиксированное соответствие трёх пар контролирует только вид полей. Правила содержимого принадлежат БД. Универсальный API не принимает прежнее верхнеуровневое `source=dokuwiki`; идентичность пользователя остаётся в серверном заголовке. Не подменять `source` внутри `data`.
- Не менять журнал, карточки, status callback, Go-код или БД. Не считать прикладной успех произвольной новой версии фактом: API может перечислить пару, а БД — отклонить конкретный ввод. На стороне wiki эту границу доказываем наблюдаемым POST и безопасным отображением 400; проверка SQL-правил уже принадлежит T24.
