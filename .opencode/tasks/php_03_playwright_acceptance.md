# PHP-03 — Воспроизводимая приёмка плагина и Playwright

**Первый тест Build:** расширить `TestQualityGate` кейсом `isolatedContainer` и запустить только его (команда 1 ниже). **Один результат:** из чистого checkout одна команда `./scripts/acceptance.sh` поднимает отдельную DokuWiki, запускает существующий полный gate и один настоящий Chromium smoke и убирает стенд. Это инфраструктура тестирования, а не изменение поведения плагина.

**Почему сейчас:** прямой выбор пользователя; `docs/todo.md`, PHP-03 открыт, PHP-04 уже отмечен выполненным. `docs/php_wiki_jobs_roadmap.md`, PHP-03 и п. 5 первой итерации требуют автоматизировать проверку страницы с двумя разными макросами. Это не утверждение, что PHP-01/02 закрыты: они не являются предпосылками тестового стенда. Один шаг, один коммит плагина после приёмки.

## Исходные данные

- Проверено чтением: `scripts/quality-gate.sh` проверяет staged/unstaged diff, делает `docker inspect` точного bind mount, PHP lint, `node --check`, `go vet`, полный `go test -race`. Имя контейнера в inspect/exec — буквально `dokuwiki`. `tests/contract/quality_gate_test.go::TestQualityGate` проверяет команды, отказ при чужом checkout и передачу статуса ошибки с помощью CLI-дублёров.
- `tests/contract/client_test.go::runPHP`, `action_test.go::TestBFFHTTPHeaders`, `ui_test.go::renderUI` и `TestSyntaxJobsMode` сами вызывают `docker exec … dokuwiki`. Последний тест действительно загружает ядро, прогоняет `p_get_instructions`/`p_render` по двум макросам и проверяет роли; тест заголовков использует `/app/www/public/inc/Input`, shell, curl и локальный PHP-сервер. `TestUIBehavior`/`TestJobsUIBehavior` используют Node и `ui_behavior.js`, не Chromium. Смена имени только в Bash даст ложную изоляцию.
- `script.js::initialize`/`checkReadiness` и `initializeJobs`/`load` запрашивают разные действия одного AJAX BFF. В реальном браузере в текущей сессии наблюдались вход под root, **две формы** со статусом Ready и отсутствие ошибок консоли; это не наблюдение журнала, не clean-checkout test и не источник тестовых credentials.
- В дереве плагина нет runner для изолированной приёмки, npm lock для Playwright и fixture-стенда. Проверенный RepoDigest локального рабочего образа: `lscr.io/linuxserver/dokuwiki@sha256:20bcd28540072a01c2364bc0ead5b280427c13b38e3c268b632a6496541d2da0`. Наличие образа не доказывает успешную инициализацию пустого `/config` или пригодность произвольного образа Playwright. Build проверяет bootstrap, версии и совместимость браузера на пустом стенде. RED/GREEN и новый smoke в Plan не запускались.

## Решения и пределы изменения

1. Файлы шага: `scripts/quality-gate.sh`, `scripts/acceptance.sh` (новый), перечисленные Go-тесты и `tests/contract/quality_gate_test.go`, при необходимости общий `_test.go` helper там же. Новые compose-манифест, bootstrap, backend-фикстура, Playwright spec/config, `package.json` и lock — под `tests/acceptance/`; runbook там же в `README.md`. Ещё `docs/todo.md` и точная копия данного плана для рабочей ссылки. Не менять production PHP/JS, ACL, правила, архитектуру, рабочий контейнер и backend. Не реализовывать отправку задания, матрицу ролей, новый CI-сервис или PHP-01/02/05.
2. Ввести `PETAR_TEST_WIKI_CONTAINER` (по умолчанию `dokuwiki`) в gate и в одном общем Go helper. Выбранный идентификатор передавать отдельным аргументом, сохранять проверку source/destination/type bind mount. Подставлять реальный ID из `docker compose -p … ps -q wiki`; пустой ID — ошибка **до** gate, а не fallback. Вложенные тесты самого gate должны контролировать своё окружение и не зависеть от ID внешнего runner. Обычный `./scripts/quality-gate.sh` остаётся без браузера.
3. Standalone runner: уникальное имя compose-проекта на запуск, именованные ресурсы только этого проекта; приватная сеть, без `container_name`, внешней сети, docker socket внутри контейнеров и опубликованных портов. Браузер — внутри стенда, обращается по DNS к wiki. Checkout смонтирован для wiki по прежнему пути; не разрешать bootstrap/chown образа менять checkout (проверить read-only bind и фактический путь через symlink). Весь writable `/config`, страницы, пользователи, сессии, кэш — одноразовые. Сначала подготовить зависимости, затем поднять wiki и HTTP fixture; дождаться HTTP с конечным deadline, не считать «контейнер запущен» готовностью. Убедиться, что тестовый конфиг подхвачен до открытия страницы. Без внешнего Postgres, DSN, backend quality gate и даже тестовой SQL-БД: DokuWiki хранит данные в файлах, backend только возвращает константы. Не брать данные, root-сессию, ключи или пароли из рабочей установки.
4. Воспроизводимость: закрепить DokuWiki по указанному digest, остальные образы по проверенным digest, версию `@playwright/test` точно и соответствующий официальный образ с Chromium; зависимости через `npm ci` с отслеживаемым lock в образе/временном каталоге (не `node_modules` в checkout). Для HTTP fixture достаточно минимального обработчика со стандартной библиотекой. В README перечислить проверенные версии Docker/Compose v2, Git, Bash, Node, Go с CGO/race и C-компилятором, архитектуру и первоначальный доступ к реестрам; MCP, предустановленный браузер хоста, внешние платные CLI не нужны.
5. Bootstrap только новой wiki: зафиксировать EN, страницу с `{{petar}}` и `{{petar>jobs}}`, временного пользователя группы `ai` с разрешением читать страницу, штатный login/ACL и `petar_url` на fixture. Не отключать проверки и не вкладывать живые учётные данные. Конфиг создавать в одноразовом хранилище штатным механизмом, без нового PHP-эндпоинта в плагине. Если добавляются PHP-файлы, соблюдать File Guard и контейнерный lint по правилам.
6. Fixture: `GET /readyz` → `200 {"status":"ready"}`; `GET /api/v1/jobs?limit=21` → HTTP 200, массив из одной фиксированной записи (`id`, `process_id` — различные валидные UUID, `tool_name=echo-test`, `status=completed`, валидные RFC3339 `created_at`/`updated_at`); неожиданному маршруту не отвечать успешной заглушкой. Остальные сценарии журнала остаются в существующих контрактах.
7. Ошибки/cleanup: конечные таймауты, без автоматического повтора smoke. Сохранить первичный exit code, стадию и безопасную диагностику (имя теста, ожидаемое/полученное, console/pageerror и HTTP status без секретов) до teardown; путь к диагностике вне checkout под `mktemp`, с правами владельца. Не выгружать cookies, `sectok`, пароли или полный trace авторизации. `trap` с обработкой EXIT/INT/TERM с момента создания ресурсов: снять **только свой** compose-проект с томами и сиротами, в т.ч. при частичном старте; ошибка cleanup при успешном тесте не должна давать PASS. Не выполнять глобальные prune/очистку кэша. `.playwright-mcp/` уже был untracked; не использовать и не добавлять.

## TDD и команды в порядке выполнения

Все команды из `/opt/php-wiki-plugin`, кроме явно указанной чистой копии. Не записывать ожидаемый RED в отчёт как факт: сохранить причины, реальные команды и результаты каждого этапа.

1. **Выбор контейнера.** В `TestQualityGate/isolatedContainer` задать `PETAR_TEST_WIKI_CONTAINER=php03-fixture`, в stub проверить фактическую цель `docker inspect` и `docker exec`, сохранить остальные проверки. Затем:
   ```
   GO111MODULE=off go test -count=1 -v ./tests/contract -run '^TestQualityGate$/^isolatedContainer$'
   ```
   Ожидаемый RED после добавления теста: ожидается `php03-fixture`, получен `dokuwiki`; не принимать «no tests to run». GREEN — override в gate с прежним default. Добавить подслучай чужого mount для override; ожидаемый отказ до lint. Проверить default в очищенном окружении и отсутствие регрессии: `GO111MODULE=off go test -count=1 -v ./tests/contract -run '^TestQualityGate$'`.
2. **Изоляция самих Go-контрактов.** До замены жёстких `exec` прогнать `TestSyntaxJobsMode` с `PETAR_TEST_WIKI_CONTAINER=php03-deliberately-absent`, убедившись, что такого контейнера нет. Ожидаемый дефект: тест способен «успешно» проверить рабочую wiki. В качестве красного теста обернуть команду проверкой ожидаемого отказа (или CLI spy, который отвергает вызов с неправильным ID). Минимальный GREEN — один helper выбора цели для всех четырёх мест, при явном отсутствующем ID ошибка на нём, без fallback. Не останавливать рабочий контейнер ради демонстрации. Обратно проверить положительный случай на отдельной wiki в п. 3; ошибка загрузки ядра/пустой БД пользователя не является полезным RED этого теста.
3. **Контракт runner.** Сделать проверку из пустого стенда: `./scripts/acceptance.sh --contracts-only` должна поднять именно новую wiki, проверить её фактический ID/checkout, выполнить весь существующий gate, закончить `QUALITY GATE PASSED` и убрать ресурсы. Изначально точки входа нет (ожидаемый RED). Ввести минимальный compose, bootstrap, ограниченное ожидание, передачу ID и cleanup; запустить ту же команду до GREEN. Проверить поддержку `/config/dokuwiki/`, `/app/www/public/`, PHP и curl старых тестов, не ослабляя assert. `--contracts-only` — диагностический этап; сам по себе не закрывает PHP-03.
4. **Первый браузерный сценарий.** Добавить spec «ai sees ready form and seeded jobs on one page». Настоящий login; ожидания по локаторам/HTTP, не sleep. На одной странице ровно одна форма и один журнал, статус формы Ready, Submit доступен, в таблице точная строка fixture по UUID/статусу. Наблюдатели до навигации: реальные успешные GET `call=plugin_petar` для `readyz` и `jobs` через wiki `lib/exe/ajax.php`, ни одного браузерного обращения к fixture/backend, нет `pageerror` и ошибок консоли на проверяемой странице. Не подменять `ajax.php` через Playwright routing. Запустить `./scripts/acceptance.sh` с подключённым spec, но до выдачи seed-строки (`jobs` пока отвечает `[]`): ожидаемый содержательный RED — readiness проходит, нужной строки нет. Минимальный GREEN — валидная строка fixture; повторить ровно ту же команду, получить успешный gate и один пройденный Chromium test.
5. **Диагностика и очистка.** В одноразовой тестовой копии временно вернуть `[]` вместо seed (не в сдаваемый diff). Выполнить `./scripts/acceptance.sh`: требуются ненулевой код, указание упавшей проверки журнала, доступная безопасная диагностика и отсутствие оставшихся ресурсов данного проекта. Если runner скрыл сбой/удалил диагностику/оставил том — это RED; исправить передачу кода, сбор артефактов и trap; прогнать отрицательный кейс и снова штатный. Для записанного имени проекта проверить `docker ps -a`, `docker network ls` и `docker volume ls` с фильтром `label=com.docker.compose.project=<фактическое имя>`; чужие ресурсы не трогать.
6. **Контроль сдаваемой версии.** Из основного checkout, при работающем штатном `dokuwiki` с нужным bind, выполнить `./scripts/quality-gate.sh` без override (проверка совместимости). Для каждого изменённого PHP — `docker exec dokuwiki php -l /config/dokuwiki/lib/plugins/petar/<путь>` (это также делает gate); для новых shell — `bash -n` если Bash; для compose — `docker compose -f tests/acceptance/compose.yaml config --quiet` с документированным окружением. Не менять `script.js`/`style.css`/метаданные: сброс кэша рабочей wiki в этом шаге не нужен.
7. **Чистый checkout без преждевременного коммита.** Подготовить к индексу только файлы шага; `git diff --cached --check` и сверить `git diff --cached --name-only`. Создать **отдельный временный** clone под `/tmp/opencode`, перенести туда `git diff --cached --binary HEAD` через `git apply --index` (не копировать неотслеживаемые файлы/артефакты). Для доказательства именно чистого checkout допустим временный fixture baseline **только в одноразовом клоне**, как в `TestQualityGate`, без hooks, push и движения веток проекта. В этом каталоге: `git status --porcelain` пуст до запуска; `./scripts/acceptance.sh`; `git status --porcelain` пуст после. Зафиксировать версии, PASS обоих этапов и отсутствие ресурсов стенда. После согласованного коммита можно воспроизвести напрямую через `git clone --local /opt/php-wiki-plugin <новый-пустой-каталог>` и ту же команду из клона. Не полагаться на ignored `.opencode/`, локальные npm-пакеты, работающий localhost:80 или состояние пользовательского браузера.
